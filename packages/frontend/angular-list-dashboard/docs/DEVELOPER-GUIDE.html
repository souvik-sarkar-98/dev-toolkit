Overview

The Universal List Dashboard powers finance dashboards (donations, expenses, accounts, donors, earnings) with a single, config-driven pattern: infinite scroll list, chip tabs, filter sheet, detail bottom sheet, and optional create/bulk-edit flows.

Signed-off pilot: apps/internal-app/src/app/feature/finance/donation/ — copy this four-folder layout (config/, data/, domain/, page/) when migrating other entities. Bind ListDashboardConfig to <na-list-dashboard> (Angular) or <ListDashboard> (@ssdev-toolkit/react-list-dashboard). See .cursor/rules/reusable-first-migrations.mdc.
Source of truth: @ssdev-toolkit/angular-list-dashboard and @ssdev-toolkit/react-list-dashboard (published UI adapters) plus internal packages/frontend/shared/list-dashboard-core (types/configs, not an npm package).
Import from the adapter for your framework; core types are re-exported for convenience.

Domain code supplies pure TypeScript config factories. Shared controllers and components handle state, URL sync, and UI.

Architecture

FilteredListDashboardController is the facade. It wires list, detail, create, and bulk-edit sub-controllers from one FilteredListDashboardConfig.

FilteredListDashboardConfig │ ├── createListPageAdapter(config.list) ──► FilteredListPageController ├── createDetailPageAdapter(config.detail) ──► ListDetailPageController ├── ListCreatePageController [if create] └── BulkEditPageController [if bulkEdit] init({ route, router, refData, config, hooks }) │ ├── ListRouteSync chip + filter criteria ↔ URL ├── ListDetailRouteSync ?donationId=…&edit=true └── ListCreateRouteSync ?create=true + presets Template binds controllers to shared components — domain pages stay thin.

Key controllers

ControllerResponsibility
FilteredListDashboardControllerFacade; exposes showCreateFab, create stepper hooks, shared context
FilteredListPageControllerChips, search, filters, pagination, selection, list reload
ListDetailPageControllerDetail sheet open/close, view sections, edit mode, documents load, save
ListCreatePageControllerCreate sheet open/close, route presets, pending deep links
BulkEditPageControllerMulti-select edit overlay; reuses detail edit hooks

Quick start — new entity checklist

  1. Create domain entity + data source with paginated fetch
  2. Add *-list.config.ts — criteria type, chips, filter hooks, loadPage
  3. Add *-list.mapper.ts — entity → ListRowItem
  4. Add forms/*-filter.form-definition.ts
  5. Add *-detail.config.ts + *-list-detail.mapper.ts
  6. Add create/update form definitions as needed
  7. Add *-dashboard.config.ts composing list + detail + create + bulkEdit
  8. Add thin *-dashboard.component.ts/html — init controller, bind template
  9. Wire route in module; set detailRouteSync.idParam

Dashboard config

Top-level shape: FilteredListDashboardConfig<TEntity, TCriteria>

export function createDonationDashboardConfig(
  deps: DonationDashboardConfigDeps,
): FilteredListDashboardConfig<Donation, DonationListFilterCriteria> {
  return {
    list: createDonationListPageConfig({ ... }),
    detail: createDonationDetailPageConfig(deps.donationData, { ... }),
    create: { kind: 'stepper', ... },
    bulkEdit: { ... },
    resolvePermissions: () => resolveDonationPermissions(deps.authorization),
    detailRouteSync: { idParam: 'donationId' },
    searchPlaceholder: 'Search donations…',
    filterSheetTitle: 'Filter donations',
    selectableWhen: ctx => canSelectDonations(ctx),
    canUpdateEntity: ctx => canUpdateOutstandingDonations(ctx),
  };
}

Permissions & FAB

create.canOpen(ctx) controls:

  • Floating action button visibility (dashboard.showCreateFab)
  • Whether create sheet can open
  • Whether ?create=true deep link is honoured

resolvePermissions() returns a permissions object passed into all canOpen / when callbacks via FilteredListDashboardContext.

Detail & edit

ListDetailPageConfig<TEntity> drives the detail bottom sheet.

View mode flow

  1. Row click → detailPage.openEntity(entity)
  2. getTitle(entity) sets sheet title
  3. buildViewSections(entity, refData) renders sections
  4. If documents.loadSection configured → async fetch → replace documents section
  5. primaryAction.when(ctx) → footer "Edit" (or custom label)

Titles vs ids

The detail sheet writes the open entity into the URL (detailRouteSync.idParam) and reads it back on reload, so the value it writes must be the id fetchById accepts. getEntityId(entity) supplies that id and falls back to getTitle when omitted — which is only safe when the title is the id (donations, expenses, earnings). Any config whose title is a display value (member name, donor name, project name, transaction ref) must implement getEntityId, otherwise deep links resolve to a name and the sheet closes itself on reload. The same id is used for documents.loadSection unless documents.resolveEntityId overrides it. 

{
  getTitle: entity => entity.fullName || entity.email,   // shown in the sheet header
  getEntityId: entity => entity.id,                      // written to ?memberId=…
  documents: { resolveEntityId: entity => entity.id, ... },
}

Hero slot

<ng-template listDetailHero let-entity> renders above the detail body in view mode — avatars, status badges, role chips. Use listDetailFooterActions only for buttons; projecting a hero there pushes it below the sections.

Edit mode flow

  1. Primary action or ?edit=true deep link → enterEdit()
  2. buildEditSummary, entityToEditValues, buildEditForm
  3. Optional prepareEdit(onReady) for async options (e.g. payable accounts)
  4. onEditValuesChange — toggle document upload, field errors
  5. onEditSave(values) → validateBeforeSave → save → list row refresh

edit.kind and edit.steps are re-read every time edit opens, so a config may expose them as getters to switch between the single form and the stepper per chip or per entity. 

// donation-detail.config.ts (abbreviated)
{
  getTitle: entity => entity.id,
  buildViewSections: (entity, refData) =>
    buildDonationListDetailSections(entity, refData),
  documents: {
    buildLoadingSection: () => buildDonationDocumentsLoadingSection(),
    loadSection: id => donationData.fetchDocuments(id).pipe(
      map(docs => buildDonationDocumentsSection(docs)),
    ),
  },
  fetchById: id => donationData.fetchDonationById(id, scope),
  findInList: (items, id) => items.find(...),
  primaryAction: {
    label: 'Edit',
    when: ctx => ctx.activeChip() === 'all_outstanding' && ctx.canUpdate(),
  },
  edit: {
    buildEditSummary, entityToEditValues, buildEditForm,
    prepareEdit, onEditValuesChange, validateBeforeSave, save,
  },
}
Documents are the only built-in async section. Other section types are built synchronously in buildViewSections. For async non-document data, either embed in the entity fetch or add a custom overlay.

View sections

Return ListDetailSection[] from buildViewSections or mappers. Three section types are supported.

1. Key-value (type: 'key_value')

Collapsible titled grid of label/value rows. Default field format is plain text.

import {
  detailTextField,
  detailHtmlField,
  detailKeyValueSection,
} from '…/list-detail.helpers';

detailKeyValueSection('summary', 'Summary', [
  detailTextField('Amount', formatCurrency(entity.amount)),
  detailHtmlField(
    'Receipt',
    '<a href="https://…" target="_blank" rel="noopener">View receipt</a>',
  ),
]);

Set format: 'html' on any ListDetailField to render sanitized HTML (links, emphasis, lists). Angular strips scripts and event handlers.

2. Documents (type: 'documents')

Renders app-document-list. Prefer configuring via ListDetailPageConfig.documents for automatic loading state.

3. Content (type: 'content')

Full-width instruction/notice block — not a label/value pair.

import { detailContentSection } from '…/list-detail.helpers';

detailContentSection(
  'banking-note',
  '<p>Verify account details with the holder before saving.</p>',
  { title: 'Instructions' },  // optional collapsible title
);

Helpers reference

FunctionReturns
detailTextField(label, value)ListDetailField with format: 'text'
detailHtmlField(label, html)ListDetailField with format: 'html'
detailKeyValueSection(id, title, fields, collapsed?)Key-value section
detailContentSection(id, html, options?)Content section

HTML fields also work in buildEditSummary for edit-mode summary rows.

Create tiers

Set create.kind in dashboard config. The framework picks the host component.

form

Single cf-form in app-list-create-sheet. Best for short creates (guest donor, earning).

stepper

Multi-step via app-list-create-stepper-sheet + CfFormStepperComponent. Used for account, donation, expense create.

component

Escape hatch — domain owns the sheet UI entirely. Route sync still works via canOpen.

Form tier

create: {
  kind: 'form',
  route: { actionParam: 'create' },
  canOpen: ctx => isGuestChip(ctx.activeChip) && perms.showCreateFab,
  buildCreateForm: () => buildDonorGuestCreateFormDefinition(),
  defaultCreateValues: () => defaultDonorGuestCreateFormValues(),
  validateBeforeCreate: values => ...,
  createSave: values => donorData.createGuestDonor(...),
}

Stepper tier

create: {
  kind: 'stepper',
  route: {
    actionParam: 'create',
    presets: [
      { param: 'forEventId', stateKey: 'forEventId', type: 'string' },
    ],
  },
  canOpen: ctx => perms.showCreateFab,
  steps: DONATION_CREATE_STEPPER_STEPS,
  buildStepDefinition: (stepId, values, ctx) =>
    buildDonationCreateStepDefinition(stepId, values, ctx),
  resolveSteps: values => resolveDonationCreateSteps(values),
  validateStep: (stepId, values, ctx) =>
    validateDonationCreateStepWithContext(stepId, values, ctx),
  defaultCreateValues: (refData, presets) => ...,
  createSave: (values, ctx) => saveDonationCreate(values, ctx),
}

Loading a step on demand

prepareStep is awaited before a step is entered, so a step whose form depends on an earlier answer can fetch just that variant instead of preloading every one. Next/Back stay disabled while it runs; a rejection keeps the user on the current step and shows the validation banner.

prepareStep: async (stepId, values, ctx) => {
  if (stepId !== 'request_details') return;
  await loadStartForm(String(values['definitionId']));
},

Custom stepper step (expense line items)

Inject a domain component via ng-template cfFormStepperStep="items" inside app-list-create-stepper-sheet. Pass extra state with:

dashboard.setCreateContextExtras({ lineItemRows: [...] });

Loading UX

The Universal List Dashboard uses a two-tier loading model: route landing shows the dashboard shell immediately; all in-framework loads use scoped, non-blocking indicators in the surface being updated.

Tier 1 — Route landing

LoadBlocking?Where feedback shows
ref_data route resolverRouter blocks navigationNo in-component spinner — resolver completes before mount
First list page (listLoading, no rows yet)NoPanel-centered spinner inside list card only; chips + search stay visible
Async filter/create optionsNoField-level when user opens filter/create sheet

Tier 2 — In-framework loads

User actionController / componentUX
Chip / filter / search refreshFilteredListPageController + app-filtered-infinite-listStale rows stay visible; top refresh bar “Updating…”; rows dimmed until fetch completes. Items are not cleared before new data arrives.
Infinite scrolllistLoadingMoreFooter inline spinner + “Loading more…”
Row tap → detailListDetailPageController.openEntityInstant — sections from row payload; no full-sheet spinner
Deep link ?donationId=tryOpenPending → fetchByIdSheet opens with body spinner until entity loads; detailPage.loading = true
Documents asyncListDetailDocumentsSection.loadingSection-level spinner in app-list-detail-sections
Save / createDetail/create sheetsButton “Saving…” / disabled — not a list-level spinner

Derived list states (app-filtered-infinite-list)

initialLoading = loading && items.length === 0   // first fetch
refreshing     = loading && items.length > 0    // chip/filter/search reload
loadingMore    = append pagination               // footer spinner
Do not use a full-page blocking spinner on filter changes. Do not hide the chip bar during listLoading. Detail sheet body spinner shows only when loading && !sections.length — existing sections (including document loading placeholders) remain visible.

Global HTTP loader

The legacy ng-http-loader full-page overlay is disabled in secured-layout. Loading feedback comes only from in-panel / in-sheet indicators above.

Extensions & escape hatches

Not everything fits the three create tiers or standard detail sheet. These patterns are intentional:

PatternExampleWhere
Detail footer actionsPay Now, Submit, ApprovedetailFooterActions slot on detail sheet
Secondary detail controllerDonor drill-down from donation row linkSecond ListDetailPageController + sheet
Domain sheets (non-create)Account transfer, banking UPIlistOverlays + MobileFormSheetComponent
Bulk custom UIDonor mergebulkActions + app-donor-merge-sheet
Draft/resubmit editExpense sent-back editDedicated expense-create-sheet (stepper), separate from list create

Prefer config + shared components first. Reach for a dedicated component sheet only when you need custom UI (radio merge, file upload flows, multi-controller interactions) that cannot be expressed as form/stepper config.

Action forms (config-driven detail/bulk/floating forms)

Named entries under actionForms replace page-owned sheets for “do one thing to this entity” flows. An action binds to one with actionFormId; the dashboard renders the sheet itself (kind: 'form' → single form + optional documents, kind: 'stepper' → shared stepper host). 

actionForms: {
  transfer: {
    kind: 'form',
    title: account => 'Record transfer',
    saveLabel: 'Confirm transfer',
    showDocumentUpload: true,
    defaultValues: (account, ctx) => ...,
    buildForm: (account, ctx) => ...,
    // sync, Promise or Observable — refreshes definition/values/loading
    onValuesChange: (account, values, ctx) => ...,
    save: ctx => saveAccountTransfer(ctx),
    success: { mode: 'reloadList', message: 'Transfer recorded' },
  },
  banking: {
    kind: 'stepper',
    steps: [...],
    customSteps: { upi: { rendererKey: 'upiRows' } },
    defaultValues: account => ...,
    defaultCustomStepData: account => ({ upi: ... }),
    buildStepDefinition: (stepId, values, ctx) => ...,
    resolveSteps: values => ...,
    save: ctx => saveAccountBanking(ctx),
    success: { mode: 'updateEntity', reopenDetail: true },
  },
}

actions: {
  detailFooter: [
    { id: 'transfer', label: 'Record transfer', run: 'transfer', actionFormId: 'transfer' },
  ],
}

detail.edit.kind: 'stepper' and bulkEdit.kind: 'stepper' reuse the same host: entering edit opens the stepper sheet instead of the single-form detail body (hasEditStepper / hasBulkEditStepper), and save still runs the configured edit/bulk save with stepper values, documents and custom-step data.

Custom step renderers

Stepper steps with kind: 'custom' declare a framework-neutral rendererKey; the Angular host resolves it from a multi-provider registry, so configs stay free of component references. 

// config (framework-neutral)
customSteps: { upi: { rendererKey: 'upiRows' } }

// app/feature providers
provideListFormCustomStepRenderer('upiRows', UpiRowsStepComponent)

A renderer component implements ListFormCustomStepComponent: @Input() data, @Output() dataChange, and optional validate(): boolean which gates Next/Save. Collected data reaches save as customStepData[stepId].

Keeping input focus while typing

The flow stores every dataChange emission and hands it back down. The host never re-applies a renderer's own emission to data, so a renderer keeps owning its editing state between keystrokes.

Renderers that list editable rows must still declare a stable trackBy. Replacing an edited row object without one destroys and rebuilds that row, and the control being typed into loses focus. Use the exported trackByIndex for positional row editors: 

<div *ngFor="let row of rows; let i = index; trackBy: trackByIndex">
